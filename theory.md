## 1. Синхронная модель выполнения и блокирующие вызовы

В синхронной модели инструкции выполняются **строго последовательно (сверху вниз)**:
- Каждая следующая инструкция начинается только после того, как полностью завершилась предыдущая.
- **Время выполнения программы** складывается из двух составляющих:
  $$\text{Время выполнения} = \text{Вычисления (CPU)} + \text{Ожидание (I/O)}$$
- **Блокирующий вызов** — это операция, которая надолго задерживает выполнение потока, не давая программе делать другую полезную работу.

### Два типа блокирующих задач:

| Характеристика | **I/O-bound (ожидание ввода-вывода)** | **CPU-bound (интенсивные вычисления)** |
|---|---|---|
| **Узкое место** | Внешняя система: сеть, диск, БД, внешний HTTP API | Процессор (CPU): математика, хеширование, рендеринг, ML |
| **Чем занят процессор в нашем процессе** | Простаивает в ожидании ответа от ОС / сети | Нагружен на 100%, выполняет инструкции |
| **Примеры в коде** | `requests.get()`, `time.sleep()`, чтение диска, SQL-запрос | `hashlib.sha256(body * 1000)`, полиномиальный хеш в цикле |
| **Чем оптимизировать в Python** | **Асинхронность (`asyncio`)** или потоки (`threading`) | **Многопроцессность (`multiprocessing` / `ProcessPoolExecutor`)** |

## 2. Способы ухода от блокировок: Потоки, Процессы, Асинхронность

### 2.1. Многопоточность (`threading`)
- В рамках одного процесса ОС создаёт несколько потоков, которые разделяют общую память (требуется защита от race conditions).
- Переключением потоков управляет **вытесняющий планировщик ОС** (в любой момент времени).
- В стандартном CPython присутствует **GIL (Global Interpreter Lock)** — глобальная блокировка интерпретатора, которая не позволяет нескольким потокам одновременно исполнять байткод Python на разных ядрах. Поэтому для CPU-bound задач на чистом Python потоки прироста не дают, но подходят для I/O-bound задач.

### 2.2. Многопроцессность (`multiprocessing`, `ProcessPoolExecutor`)
- Запускаются отдельные дочерние процессы ОС.
- У каждого процесса — **свой интерпретатор Python и своё адресное пространство памяти**, поэтому **проблема GIL отсутствует**.
- Идеально подходит для **CPU-bound** задач, но создание процессов и пересылка данных между ними (IPC / сериализация) дороже по ресурсам ОС, чем потоки и корутины.

### 2.3. Асинхронность (`asyncio`)
- Работает в **одном процессе и одном потоке**.
- Использует **кооперативную многозадачность**: переключением задач занимается не ОС, а сама программа (через цикл событий — **event loop**).
- Задача сама добровольно уступает управление в явно помеченных **точках переключения** (`await`).
- Минимальные накладные расходы памяти и CPU — можно держать тысячи одновременных сетевых соединений без затрат на создание тысяч потоков ОС.

## 3. Составные части асинхронной модели в Python (`asyncio`)

1. **Корутина (`async def`)** — функция/задача, которая умеет приостанавливать своё выполнение и возобновлять его позже с того же места. Вызов корутины `fetch(...)` не запускает код сразу, а возвращает объект корутины.
2. **Точка переключения (`await`)** — явная метка места, где задача ожидает завершения неблокирующей операции и готова уступить поток выполнения другим задачам.
3. **Цикл событий (`event loop`, диспетчер)** — механизм, который ведёт очередь задач, запускает готовую задачу, принимает обратно управление, когда задача доходит до `await`, и возвращает задачу в очередь, когда ожидаемое событие (например, ответ по сети) наступило.
4. **Кооперативность** — задачи не вытесняются принудительно; если одна из задач запустит долгий синхронный цикл без `await`, весь event loop встанет.

## 4. Главные практические правила и разбор ловушек из ДЗ

### Ловушка 1: Последовательный `await` в цикле `for` (Задание 0)
```python
# НЕПРАВИЛЬНО: запросы идут строго по очереди!
for url in URLS:
    await fetch(client, url)
```
**Почему не быстрее:** `await` внутри цикла `for` заставляет корутину дождаться полного окончания текущего запроса перед переходом к следующей итерации. В очереди event loop в каждый момент времени находится только один запрос.

```python
# ПРАВИЛЬНО (вариант 1 — asyncio.gather):
await asyncio.gather(*(fetch(client, url) for url in URLS))

# ПРАВИЛЬНО (вариант 2 — asyncio.TaskGroup, Python 3.11+):
async with asyncio.TaskGroup() as tg:
    tasks = [tg.create_task(fetch(client, url)) for url in URLS]
```
**Почему быстрее:** Все 20 задач регистрируются в event loop сразу. Как только первая задача отправляет HTTP-запрос и встаёт на `await`, управление тут же передаётся второй, третьей и т.д. Все 20 запросов ждут ответа от сервера параллельно во времени (конкурентно).

### Ловушка 2: Особенности редиректов в `httpx` vs `requests` (Задания 0–3)
Сервис `https://picsum.photos/seed/{i}/800/600` возвращает HTTP-статус `302 Found` (редирект на CDN с картинкой).
- Библиотека `requests` по умолчанию следует по редиректам (`allow_redirects=True`).
- Библиотека `httpx` по умолчанию **не** переходит по редиректам (`follow_redirects=False`).
Поэтому во всех клиентах `httpx.AsyncClient(follow_redirects=True)` обязательно указывать `follow_redirects=True` — иначе вместо скачивания картинок (~100 КБ) клиент получит пустой ответ `302`, сравнение времени будет нечестным, а `resp.raise_for_status()` в `httpx` выбросит `HTTPStatusError` на статус `302`.

### Ловушка 3: Грабли реального сетевого I/O (Задание 2)
В реальной сети сервер может не ответить, ответить с ошибкой или зависнуть:
1. **Таймауты (`timeout`)**: Сеть не должна ждать вечно. Передача `timeout=3.0` в `client.get(url, timeout=3.0)` (или `asyncio.wait_for`) гарантирует, что «зависший» запрос (например, `https://httpbin.org/delay/10`) упадёт по `httpx.ReadTimeout` через 3 секунды.
2. **Ретраи с экспоненциальным backoff**: При временных сбоях сети не стоит спамить сервер мгновенными повторами. Пауза между попытками увеличивается экспоненциально: $2^0 = 1\text{ с} \rightarrow 2^1 = 2\text{ с} \rightarrow 2^2 = 4\text{ с}$ через `await asyncio.sleep(2 ** attempt)`.
3. **Изоляция падений (`return_exceptions=True`)**: По умолчанию `asyncio.gather` при первом необработанном исключении пробрасывает его наверх. С флагом `return_exceptions=True` исключения возвращаются как обычные элементы списка результатов:
   ```python
   outcomes = await asyncio.gather(*coroutines, return_exceptions=True)
   ```
   Это позволяет отделить успешные ответы от ошибок (`isinstance(outcome, Exception)`), не теряя результаты остальных 20 успешных запросов.

### Ловушка 4: Блокировка event loop синхронными и CPU-bound вызовами (Задание 3*)

Памятка по выносу синхронных операций из асинхронного кода:

| Тип синхронного вызова | Куда выносить | Инструмент в `asyncio` |
|---|---|---|
| **Блокирующий I/O-bound** (например, старый синхронный драйвер или `requests.get`) | В отдельный поток | `await asyncio.to_thread(sync_io_fn, arg)` |
| **Тяжёлый CPU-bound** (например, `hashlib.sha256(body * 1000)`) | В отдельный процесс (пул процессов) | `await loop.run_in_executor(ProcessPoolExecutor(), heavy, body)` |
| **Лёгкий и быстрый код** (парсинг пары строк, сложение чисел) | Никуда | Оставить как есть в корутине |

Когда функция `heavy(body)` вызывается напрямую внутри корутины, она занимает единственный поток на всё время расчёта хешей: корутина `ticker()` не может проснуться из `await asyncio.sleep(0.1)`, и точки перестают печататься. При выносе через `loop.run_in_executor(pool, heavy, body)` с `ProcessPoolExecutor` вычисления уходят в дочерние процессы ОС, а основной поток с event loop остаётся полностью свободным и продолжает печатать точки `ticker` каждые `0.1` секунды.
